Del 3

Normalformerna

Funktionellt beroende, 1NF, 2NF och 3NF

Funktionellt beroende

A → B – "om du vet A, så vet du B"

Beroende i kvittotabellenBetyder
CustomerId → Customer, EmailKund 51 är alltid Joakim med samma e-post
InvoiceId → InvoiceDate, CustomerIdFaktura 65 har ett datum och en kund
TrackId → Track, Album, GenreLåt 2100 är alltid Crazy Train på Tribute
Album → ArtistEtt album har en artist
(InvoiceId, TrackId) → UnitPrice, QuantityPris och antal för en låt på en faktura

Inte beroende: Artist → Track. Ozzy Osbourne har många låtar.

Funktionellt beroende i C#

Ett funktionellt beroende är som en Dictionary: nyckeln ger dig värdet.

Dictionary<int, Customer> kunder = …;
kunder[51].Email     // CustomerId → Email

Dictionary<(int, int), decimal> priser = …;
priser[(65, 2100)]   // (InvoiceId, TrackId) → UnitPrice – sammansatt nyckel

Så hittar du beroendena: fråga "Om jag vet X – kan det finnas två olika Y?" Nej → X → Y. Utgå från vad datan betyder, inte bara från exempelraderna: alla låtar ovan kostar 0.99, men genren bestämmer inte priset.

Normalformerna på en bild

1NF

Ett värde per cell. Inga listor i en kolumn, inga Telefon1, Telefon2. Varje rad har en primärnyckel.

2NF

1NF + hela nyckeln. Varje kolumn beror på hela primärnyckeln. Gäller när nyckeln har flera kolumner.

3NF

2NF + inget annat än nyckeln. Ingen kolumn beror på en annan kolumn som inte är nyckel.

"The key, the whole key, and nothing but the key."

Edgar F. Codd, IBM – relationsmodellen 1970. Det finns fler normalformer (BCNF, 4NF, 5NF), men 3NF räcker nästan alltid.

0NF: en lista i en cell

InvoiceIdInvoiceDateCustomerTracks
652021-10-08Joakim JohanssonI Don't Know, Flying High Again, No More Tears, Crazy Train
  • Alla fakturor med Crazy Train? LIKE '%Crazy Train%' – och hoppas att ingen stavat fel.
  • Hur räknar man låtar, eller sätter pris per låt?
  • En lista kan inte innehålla främmande nycklar.

Track1, Track2, Track3 … är lika dåligt. Joakims faktura 271 har 14 låtar.

public string Tracks { get; set; }                    // 0NF: "I Don't Know, Flying High Again, …"
public List<Track> Tracks { get; set; } = new();       // så gör du i C# – i databasen blir det fler rader

1NF: en rad per låt

Kvittotabellen med en rad per låt är i 1NF: varje cell har ett värde. Men vad är primärnyckeln?

Räcker InvoiceId?

Nej – faktura 65 har fyra rader.

Räcker TrackId?

Nej – samma låt kan säljas på många fakturor.

PK = (InvoiceId, TrackId)

En sammansatt nyckel (composite key) – två kolumner som tillsammans är unika. Tabellen är i 1NF, men fortfarande full av upprepningar.

Kvar finns beroenden "i två steg" – transitiva beroenden:

Priset: datan ligger i flera tabeller. För att visa ett kvitto måste vi sätta ihop dem – med JOIN, senare idag.

Arbetsgång: normalisera steg för steg

  1. Lista alla kolumner och hitta det som gör varje rad unik – primärnyckeln.
  2. 1NF: dela upp listor och upprepade kolumner till fler rader.
  3. Skriv ner alla funktionella beroenden: vad bestämmer vad?
  4. 2NF: flytta kolumner som beror på en del av nyckeln till en egen tabell.
  5. 3NF: flytta kolumner som beror på något annat än nyckeln till en egen tabell.
  6. Ge varje ny tabell en PK, koppla ihop med FK och rita ER-diagrammet.

Den här arbetsgången använder ni i parövningen.

Medveten denormalisering

Chinook är normaliserad – men inte överallt:

I ChinookVarför?
Invoice.BillingAddress, BillingCity …Adressen när köpet gjordes – även om kunden flyttar. En annan uppgift än kundens adress nu.
InvoiceLine.UnitPrice och Track.UnitPricePriset vid köpet respektive dagens pris.
Customer.PostalCode och CityPostnumret bestämmer orten – transitivt. Men en tabell med världens alla postnummer vore mer jobb än nytta.

Normalisera först – denormalisera medvetet. Det är okej att avvika från 3NF om du kan förklara varför. Det är det kursmålet menar med att motivera valen.

Snabbquiz: vilken normalform bryts?

Skriv i chatten först. Primärnyckeln är understruken.

1. Student(StudentId, Namn, Telefon) – Telefon: "070-123 45 67, 073-765 43 21"

Normalisering bestämmer var datan ligger – constraints bestämmer vad som får stå där

Databasen kontrollerar reglerna för alla program som skriver till den – webbsida, app eller någon som skriver SQL för hand.

NOT NULL

Customer.Email är NOT NULL i Chinook. En kund utan e-post:

INSERT INTO Customer (CustomerId, FirstName, LastName)
VALUES (60, N'Ada', N'Lovelace');
Msg 515, Level 16, State 2, Line 1
Cannot insert the value NULL into column 'Email', table 'Chinook.dbo.Customer'; column does not allow nulls. INSERT fails.
The statement has been terminated.

Fråga för varje kolumn: kan en rad finnas utan det här värdet? En kund utan e-post – nej. En kund utan företag – ja.

UNIQUE

Chinook saknar regeln att e-posten ska vara unik – vi lägger till den:

ALTER TABLE Customer
ADD CONSTRAINT UQ_Customer_Email UNIQUE (Email);

-- Testa: en ny kund med Joakims e-post
INSERT INTO Customer (CustomerId, FirstName, LastName, Email)
VALUES (60, N'Ada', N'Lovelace', N'joakim.johansson@yahoo.se');
Msg 2627, Level 14, State 1, Line 5
Violation of UNIQUE KEY constraint 'UQ_Customer_Email'. Cannot insert duplicate key in object 'dbo.Customer'. The duplicate key value is (joakim.johansson@yahoo.se).
The statement has been terminated.

PK eller UNIQUE? En PK per tabell, men många UNIQUE. E-post passar dåligt som PK – den kan ändras.

CHECK

ALTER TABLE InvoiceLine
ADD CONSTRAINT CK_InvoiceLine_Quantity CHECK (Quantity > 0);

ALTER TABLE Track
ADD CONSTRAINT CK_Track_UnitPrice CHECK (UnitPrice >= 0);

-- Testa: en fakturarad med antal 0
INSERT INTO InvoiceLine (InvoiceLineId, InvoiceId, TrackId, UnitPrice, Quantity)
VALUES (2241, 42, 1, 0.99, 0);
Msg 547, Level 16, State 0, Line 8
The INSERT statement conflicted with the CHECK constraint "CK_InvoiceLine_Quantity". The conflict occurred in database "Chinook", table "dbo.InvoiceLine", column 'Quantity'.
The statement has been terminated.

En constraint kan bara läggas till om all befintlig data redan följer regeln.

DEFAULT

ALTER TABLE InvoiceLine
ADD CONSTRAINT DF_InvoiceLine_Quantity DEFAULT 1 FOR Quantity;

ALTER TABLE Invoice
ADD CONSTRAINT DF_Invoice_InvoiceDate DEFAULT GETDATE() FOR InvoiceDate;

-- Quantity utelämnas – och blir 1
INSERT INTO InvoiceLine (InvoiceLineId, InvoiceId, TrackId, UnitPrice)
VALUES (2241, 42, 1, 0.99);
  • GETDATE() = dagens datum och klockslag, som DateTime.Now.
  • DEFAULT används bara när kolumnen utelämnas. Skriver du NULL blir det NULL.

Snabbquiz: vilken constraint?

1. Ett pris får inte vara negativt.

CHECK (Pris >= 0)

2. Två användare får inte ha samma användarnamn.

UNIQUE

3. Varje låt måste ha ett namn.

NOT NULL

4. Anges inget datum ska dagens datum användas.

DEFAULT GETDATE()

5. En faktura måste tillhöra en kund som finns.

FOREIGN KEY – och NOT NULL om den måste ha en kund.

6. Ett betyg måste vara F, E, D, C, B eller A.

CHECK (Betyg IN ('F', 'E', 'D', 'C', 'B', 'A'))

7. En ny kund ska vara aktiv från början.

Aktiv BIT NOT NULL DEFAULT 1

8. Samma låt får inte finnas två gånger i samma spellista.

Sammansatt PRIMARY KEY (PlaylistId, TrackId) – eller UNIQUE på de två kolumnerna.

Säker rutin: SELECT först, sedan transaktion

  1. Skriv villkoret som en SELECT och kontrollera raderna.
  2. Byt SELECT * mot UPDATE … SET eller DELETE. Behåll WHERE.
  3. Kör i en transaktion och titta innan du sparar.
  4. Läs (1 row affected). Väntade du 1 och det står 59 – ROLLBACK.
-- 1. Vilka rader?
SELECT * FROM Customer WHERE CustomerId = 51;

-- 2–3. Ändra i en transaktion
BEGIN TRANSACTION;

UPDATE Customer
SET Email = N'joakim@nymail.se'
WHERE CustomerId = 51;

SELECT * FROM Customer WHERE CustomerId = 51;

ROLLBACK;   -- ångra …
-- COMMIT;  -- … eller spara

En transaktion är som ett utkast: inget sparas förrän COMMIT. Avsluta alltid med COMMIT eller ROLLBACK – en öppen transaktion låser raderna för andra.

Iron Maiden – i en fråga

Torsdag: två frågor

SELECT ArtistId
FROM Artist
WHERE Name = 'Iron Maiden';
-- 90

FROM Album

Idag: en fråga

SELECT Album.Title
FROM Album
INNER JOIN Artist
    ON Album.ArtistId = Artist.ArtistId
WHERE Artist.Name = 'Iron Maiden'
ORDER BY Album.Title;
-- 21 album

Normaliseringen delade upp datan. JOIN sätter ihop den igen när vi läser.

JOIN i C#

Med referens: följ den direkt

album.Artist.Name   // "Iron Maiden"

Det är just det databasen inte kan spara – den har bara ArtistId. Därför JOIN.

Med id: LINQ Join

var svar = albums
    .Join(artists,
          al => al.ArtistId,   // FK
          ar => ar.ArtistId,   // PK
          (al, ar) => new { al.Title, Artist = ar.Name })
    .Where(x => x.Artist == "Iron Maiden")
    .OrderBy(x => x.Title);

Sammanfattning

  • Normalisering: varje uppgift på ett ställe – inga uppdaterings-, insättnings- eller borttagningsanomalier.
  • Funktionellt beroende A → B: om du vet A vet du B.
  • 1NF ett värde per cell · 2NF hela nyckeln · 3NF inget annat än nyckeln.
  • Normalisering = byt kopior mot referenser, precis som i C#.
  • Constraints – NOT NULL, UNIQUE, CHECK, DEFAULT – gäller för alla program. Ge dem namn.
  • CRUD = INSERT, SELECT, UPDATE, DELETE. SELECT först, ändra i en transaktion.
  • JOIN sätter ihop tabellerna igen: ON FK = PK.
